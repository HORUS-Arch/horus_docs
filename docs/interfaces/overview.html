ROS 2 interfaces#

Every node, topic, service and action of a running rig. Names are as launched by rig.launch.py; <name> is an instance name from the rig file. Message layouts: Messages, services and actions. Each package’s own page (under Packages) lists its parameters.

        flowchart LR
  UI["web UI"] <-->|rosbridge| SUP["/horus/supervisor<br/>modes + trees"]
  UI <-->|rosbridge| SES["/horus/session"]
  SUP -->|ExecuteBehavior| GEN["/horus/generator_server"]
  SUP -->|Calibrate| HN["/human/&lt;name&gt;"]
  SUP -->|state| SES
  SES -->|subject_id, load_calibration| HN
  DRV["/sensors/&lt;name&gt;"] --> HN
  HN --> GEN
  GEN -->|reference| CM["controller_manager<br/>SafetyController last"]
  CM -->|/joint_states, wrench| GEN
  CM -.->|/diagnostics| SUP
  SUP -.->|estop, state| CM
  SES -.->|records everything| BAG[("rosbag2")]

Conventions#

  • /sensors/<name>: raw driver data. /human/<name>: HORUS-processed human state. /horus/<node>: system nodes. The robot keeps its own ros2_control names.

  • Channel names (segments, muscles, sides) use the human_msgs vocabulary: right_upper_leg, rectus_femoris_r, left.

  • QoS: data streams use sensor-data QoS (best effort); state topics (*/state, behavior_state) are latched (transient local, reliable).

  • Units are SI; human_msgs documents its exceptions (mV, kPa).

Inspecting the graph#

ros2 node list                                   # every node of the rig
ros2 topic list -t | grep -E "^/(horus|human|sensors)"
ros2 topic echo /horus/supervisor/state --once   # current mode and why
ros2 topic hz /position_controller/commands      # generation rate while a behavior runs
ros2 action list -t                              # execute_behavior, calibrate
ros2 control list_controllers                    # which controller is active
ros2 lifecycle get /horus/generator_server       # lifecycle state of a managed node
